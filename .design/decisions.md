# Wynd and crosswind-workers design decisions

Settled on 2026-10-11 after a design review of pywrangler, the stock `workers-runtime-sdk`, EdgeKit and pyodide-pack. Nothing here is implemented yet.

## Packages and names

Wynd replaces pywrangler. It is published on PyPI as `wynd`, and its command is `wynd`. Its source lives in [wynd/](../wynd).

crosswind-workers replaces `workers-runtime-sdk` and is written from scratch. It is published on PyPI as `crosswind-workers` and imported as `workers`, because workerd imports that exact name at startup. Its source lives in [crosswind-workers/](../crosswind-workers), and `[tool.uv.build-backend] module-name = "workers"` maps the distribution to the import name.

Both packages support Python 3.12, 3.13 and 3.14, with the same target selection as pywrangler. Both must declare `requires-python = ">=3.12"`, because crosswind runs inside Pyodide on the 3.12 target. crosswind does not depend on `typing_extensions`, so it uses only typing features that exist in 3.12, such as PEP 695 generics.

Wynd's configuration lives under `[tool.wynd]` in `pyproject.toml`, and its working files live in `.wynd/`.

## Wynd

### Resolution and SDK selection

Wynd resolves packages the way pywrangler does. It runs `uv pip compile` against the Emscripten interpreter for the target, adds the target's Pyodide index, passes `--no-build` unless the project opts into source builds, and writes `pylock.toml`. The project commits `pylock.toml`. The per-target interpreters and index URLs come from pywrangler's [metadata.py](../../workers-py/packages/cli/src/pywrangler/metadata.py) and the resolve flow from [resolve.py](../../workers-py/packages/cli/src/pywrangler/resolve.py), both at commit `cb2db3c`.

The project declares exactly one SDK as a direct dependency, either `crosswind-workers` or `workers-runtime-sdk`. Wynd injects neither.

- If the project declares neither, Wynd exits with an error asking the user to add one.
- If the project declares both directly, Wynd exits with an error.
- If a library pulls in the SDK the project did not choose, Wynd removes it with uv's `--excludes` ([tested](research/removing-a-dependency-with-uv.md)).

### Host environment

Wynd creates no host virtual environment. The user runs `uv sync`, which builds the project's normal `.venv`, so editors, Pyright and local tests find packages without configuration. Wynd warns when the `.venv` Python minor version differs from the target's, for example:

```
warning: .venv is Python 3.13 but wrangler.jsonc targets 3.12 (python_workers, 2025-06-01).
Editor types may differ from production. To match: uv venv --python 3.12 && uv sync
```

pywrangler uses a separate `.venv-workers` because it matches the target's Python version and pins host packages to the vendored versions. Wynd accepts that the host and Pyodide versions can drift. The drift affects what the editor shows, never the upload.

### Project layout

```
my-worker/
├── pyproject.toml      # dependencies = ["crosswind-workers", ...]
├── uv.lock             # host lock from uv, committed
├── pylock.toml         # Pyodide lock from wynd, committed
├── wrangler.jsonc
├── src/
│   ├── main.py
│   └── env.py          # generated by wynd types, committed
├── .venv/              # from uv sync, ignored
├── python_modules/     # full Pyodide install used by dev, ignored
└── .wynd/              # ignored
    ├── synced          # sync token
    ├── site-packages/  # install in progress, moved to python_modules/ on success
    └── build/          # pruned tree for upload, wiped when the next upload starts
        ├── wrangler.jsonc
        ├── src/
        └── python_modules/
```

### When sync runs

Wynd stores a content hash in `.wynd/synced`. The hash covers `pyproject.toml`, `pylock.toml`, the resolved target (Python version, compatibility date and flags) and the Wynd version. Sync reruns when any of them changes. pywrangler compares timestamps of the two TOML files only, so a compatibility-date change leaves it on the old target.

### Config and environment flags

`-c`/`--config` picks a different Wrangler config file. `-e`/`--env` picks a named environment inside the file, and that environment can override the compatibility date, which selects the Python version. Wynd reads both flags from the command it forwards, uses them to choose the target and to stage the config, and passes them to Wrangler unchanged. pywrangler ignores them during resolution, so `pywrangler deploy --env next` can install 3.12 wheels for a 3.14 environment.

### Staged config

Wrangler resolves relative paths from the directory of the config file. The staged config in `.wynd/build/` therefore needs its path keys rewritten to absolute paths that point back at the project. `main` and `base_dir` stay relative so they resolve into the staged source. Wynd rewrites a fixed list of known keys, including keys inside `env` sections and `previews`, such as `assets.directory`, container image paths, `site.bucket` and `d1_databases[].migrations_dir`. The full list is in [wynd.md](wynd.md) and comes from the [config research](research/wrangler-config-discovery.md). `build.cwd` resolves from the process working directory, so Wynd runs Wrangler from the user's working directory and leaves it alone. `main` points at the staged `src/`. A relative path under a key Wynd does not recognize fails the build.

### Commands

| Command | Behavior |
| --- | --- |
| `wynd sync` | Resolves and installs the target packages |
| `wynd types` | Generates `src/env.py` (see [Typed bindings](#typed-bindings)) |
| `wynd dev` | Syncs, then runs `wrangler dev` on the full tree from the working directory |
| `wynd deploy [--dry-run]` | Syncs, prunes into `.wynd/build/` and runs Wrangler with the staged config. `--dry-run` reports bytes before and after pruning. |
| `wynd versions upload`, `wynd preview` | Same flow as deploy, because both upload code |
| Anything else | Passed straight to Wrangler, without sync |

`wynd dev` never runs pruned code in v1. Wrangler reloads on source changes without Wynd in the loop, so a pruned tree would raise `ImportError` for any import added during a dev session. Wynd has no `publish`, because wrangler 4.127.1 rejects it as an unknown argument, and no `init`, because create-cloudflare's Python template sets up pywrangler and the stock SDK.

### Runtime dependencies

Wynd has one runtime dependency. [json-with-comments](https://github.com/n-takumasa/json-with-comments) (import name `jsonc`, no dependencies of its own) parses `wrangler.jsonc`. It handles comments, comment markers inside strings, and trailing commas. TOML configs are read with the stdlib `tomllib`. The CLI uses `argparse`, with `parse_known_args` forwarding unknown arguments to Wrangler. The staged config is always written as `wrangler.json`, because the stdlib can't write TOML. uv is not a dependency, because users run Wynd through uv (`uvx wynd`), so a second copy would only add about 20 MB and a second uv version. Wynd requires uv 0.12.3 or later on PATH, the same minimum pywrangler checks. `uv pip compile --excludes` first appears between 0.9.0 and 0.10.0, so 0.12.3 covers it. Before running uv, Wynd checks `uv --version` and stops with an upgrade message if it is older. Node.js and `npx` are also required on PATH, as with pywrangler.

### Wrangler version

Wynd runs an exact pinned version through `npx --yes wrangler@X.Y.Z`. The pin is wrangler 4.129.0, the first release whose bundled workerd (1.20260903.1) accepts compatibility date 2026-09-08 ([research](research/wrangler-release-for-2026-09-08.md)). Wrangler 4.127.1 supports dates only up to 2026-09-04. Each bump runs a dry-run test that checks module names and types in the output. Wynd depends on these Wrangler behaviors:

| Behavior | Documented | Failure if it changes |
| --- | --- | --- |
| `python_modules/` beside the config is collected | Yes | Nothing uploads |
| Every file under it uploads as data at its own path, minus `python_modules.exclude` | No | `.dist-info` and package resource files disappear |
| The module root is the entrypoint's directory | Partly | The staged `src/` layout breaks |
| Config file precedence and `--env` merging | Yes | Wynd and Wrangler pick different targets |
| `python_modules/workers/*.js` uploads as ES modules (stock SDK only) | No | Stock Workflows break |
| The newest compatibility date the bundled workerd supports | Indirectly | 3.14 dates fail locally |
| The `deploy --dry-run --outdir` output layout | Partly | The per-bump module check breaks |

### Compatibility flags

Wynd requires no compatibility flags. A local test with `wrangler dev` 4.127.1 showed that a vendored `python_modules/workers` package wins on 3.12, 3.13 and 3.14, with and without `enable_python_external_sdk`, and that both `enable_python_external_sdk` and `python_process_pth_files` work when set explicitly with a 2025-06-01 date.

## Tree-shaker

Wynd's tree-shaker is a new analyzer built on stdlib `ast`. It does not reuse EdgeKit, whose checkout has no tests and whose source transformations corrupt multiline strings and same-line statements.

The shaker prunes only vendored packages in `python_modules/`. Project code under `src/` is copied unchanged.

Roots are the entrypoint, the `[tool.wynd] keep` list, and every module named on an `import` line of a `.pth` file. `.pth` files are parsed with `ast` and never executed. A `.pth` line that is not a plain import fails the build and names the file.

From the roots, the shaker follows imports across distributions. It then applies these rules:

- It drops unreachable modules and whole distributions, tests, docs, `__pycache__`, `.pyi` files and `py.typed` markers.
- It keeps `.dist-info` metadata, because libraries call `importlib.metadata.version()` at runtime. A distribution whose modules were all dropped loses its `.dist-info` too, so no library sees it as installed and then hits `ImportError`.
- It keeps `.so` extensions built for Pyodide. Any other kept `.so`, such as one built for the host, fails the build.
- It keeps every non-Python file under a top-level package when any module of that package is kept. This rule keeps templates, data files, tzdata's zone files and the stock SDK's `workers/workflows.js`.

The import graph follows these edge rules:

- Imports under `if TYPE_CHECKING:` or `if typing.TYPE_CHECKING:` are skipped. Other spellings are followed.
- Imports inside `try`/`except ImportError` and inside function bodies are followed like any other import.
- An `import_module` or `__import__` call with a computed name that starts with literal text follows every module that start allows. pydantic loads most of its public names this way, with `import_module(f".{name}", package=...)`, so without this rule a pruned pydantic fails at import.
- A name with no vendored file is recorded as unresolved in the shake plan and doesn't fail the build. That covers the stdlib, `js`, `pyodide`, `_cloudflare` and optional dependencies that aren't installed.
- `from pkg import *` follows `pkg` and every submodule named in its literal `__all__`. `from pkg import name` also follows `pkg.name` when that is a module.

Retained files are copied verbatim. v1 does no symbol slicing, minification or execution tracing.

## Typed bindings

`wynd types` reads the Wrangler config in Python and writes `src/env.py`, which the project commits. Wynd holds only the table that maps config sections to class names. The classes live in `workers.bindings`, so the generated module also works at runtime when `WorkerEntrypoint[Env]` evaluates it.

```python
# src/env.py. Generated by wynd types. Do not edit.
from __future__ import annotations

from typing import TYPE_CHECKING, Protocol

from workers.bindings import DurableObjectNamespace, KVNamespace

if TYPE_CHECKING:
    from main import Counter

class Env(Protocol):
    COUNTER: DurableObjectNamespace[Counter]
    CACHE: KVNamespace
```

- Class names follow Cloudflare's names: `KVNamespace`, `D1Database`, `R2Bucket`, `DurableObjectNamespace`.
- Attribute names copy the binding names from the config exactly.
- A Durable Object class from the same project is imported under `TYPE_CHECKING`, which avoids a circular import with `main.py`.
- Secret names come from `.dev.vars`.
- `dev` and `deploy` render the file and write it only when the text differs, and `wynd types --check` fails CI when it differs. No timestamps are compared. `wynd dev` renders once at startup, so a config change during a dev session needs a restart or `wynd types`.
- `wynd types` requires crosswind-workers, because the stock SDK has no `workers.bindings`.

v1 has typed classes for these config sections:

| Config section | Class |
| --- | --- |
| `kv_namespaces` | `KVNamespace` |
| `d1_databases` | `D1Database` |
| `r2_buckets` | `R2Bucket` |
| `queues.producers` | `Queue` |
| `durable_objects.bindings` | `DurableObjectNamespace[Class]` |
| `services` and the assets binding | `Fetcher` |
| `workflows` | `Workflow` |
| text `vars` and secrets | `str` |

Every other binding is a `Binding`, a loosely typed passthrough wrapper. That covers Workers AI, Vectorize, Analytics Engine, Images, rate limiting, Hyperdrive, version metadata and any section Wynd doesn't recognize, so a new Cloudflare product doesn't break `wynd types`. A JSON var such as `"FLAGS": {"beta": true}` arrives as a Python value and is typed from its literal value, so code reads `FLAGS["beta"]` where the stock SDK allowed `FLAGS.beta`. The env wrapper can't tell a JSON object from another plain-object binding, so version metadata also arrives as a dict whose keys read as attributes, and typegen types it that way, not as `Binding`. A JS value a binding returns that conversion leaves as JS comes back as a `Binding`; the stock SDK wrapped it in the parent's class.

Python typing cannot express a Durable Object RPC stub the way TypeScript's `DurableObjectStub<T>` does. `get_by_name` is typed as returning the class itself, so the checker catches wrong method names and argument types but not calls to sync methods through the stub.

## crosswind-workers

### Scope

v1 matches the stock SDK's full `__all__`:

- `WorkerEntrypoint`, `DurableObject` and `WorkflowEntrypoint`
- `Request`, `Response`, `FetchResponse` and `fetch`
- `Blob`, `File` and `FormData`
- the `asgi` and `wsgi` adapters
- module-level `env` and `wait_until`
- `import_from_javascript`

Workflows are implemented in pure Python, so the wheel contains only Python. Module-level `on_fetch` style handlers are planned for after v1. The stock `handler` decorator for them is exported now, with its stock behavior, because it is in the stock `__all__`.

### Contract with workerd

workerd runs `from workers import DurableObject, WorkerEntrypoint, WorkflowEntrypoint, python_from_rpc, python_to_rpc` and finds handlers with `issubclass` against those exact classes. crosswind must export all five names even where a feature is incomplete. workerd passes class-method arguments through `python_from_rpc` and return values through `python_to_rpc`, which must produce a JS `Response` for `fetch`. `connect`, Durable Object `alarm`, the `webSocket*` methods and Workflow `run` receive raw JS proxies, so crosswind wraps them in `__init_subclass__`. crosswind holds no JS objects at import time, because snapshot serialization rejects them.

On compatibility dates before 2025-08-14, workerd calls `on_fetch` on the class instead of `fetch`. The rename covers `fetch` and `connect` on every entrypoint, plus `alarm` and the three `webSocket*` handlers on Durable Objects (`makeEntrypointProxyHandler` in `python-entrypoint-helper.ts`, workerd `5f4f3d3`). `scheduled` and `queue` keep their names. For each renamed handler a class has, including one inherited from a mixin, crosswind adds an `on_<name>` alias that calls the short name through `relaxed_call`, because workerd passes `on_fetch` the arguments `(request, env, ctx)`. An `on_<name>` the class defines itself wins, so user code always uses the short names.

Evidence comes from workerd at commit `d08010b` (`src/pyodide/internal/introspection.py`, `src/pyodide/python-entrypoint-helper.ts`) and from the local `wrangler dev` test.

### Compatibility with the stock SDK

The stock SDK's behavior is the minimum crosswind supports. Every stock name and call signature works. camelCase JS calls on `ctx`, `env` and binding wrappers pass through to the JS object. Typed snake_case methods and optional generics sit on top, so `ctx.storage.delete_all()` and `ctx.storage.deleteAll()` both work, and so do `class X(DurableObject)` and `class X(DurableObject[Env])`. `__init_subclass__` calls `super()`, and the entrypoints are generic only to type checkers (a `TYPE_CHECKING` base; at runtime `DurableObject[Env]` returns the class), so `Generic` runs in either base order. A class that is generic at runtime can't follow `Generic[S]` in a base list, because Python reports an inconsistent MRO. Type checkers see `DurableObject` as generic and report the same error for `Generic` first, so typed code puts `Generic` last.

The API is async-only, which avoids 3.12's missing `run_sync`.

crosswind fixes every bug flagged in the [stock SDK catalog](research/stock-sdk-behavior.md) instead of reproducing it. Nine of them raise an error today, so no working code depends on them: a JS `File` received over RPC, `len(form_data)`, `Response(blob)`, `request.method` for a non-standard method, a `memoryview` or `bytearray` as a Blob part, a non-JS exception inside `step.do`, an implicit Workflow dependency on a step name that isn't a Python identifier, `env` or a Durable Object namespace sent over RPC, and entering `patch_env`. Three return a wrong value today, and crosswind fixes those too:

- `Response.redirect` returns a crosswind `Response`. Code that used the raw JS object keeps working through `js_object` and camelCase passthrough.
- Binding wrappers read non-callable attributes on every access, so a D1 cursor's counters stay current.
- The WSGI adapter's buffered-body fallback runs when the request has no stream.

The stock SDK's own tests import private names, so crosswind serves them too: `workers.rpc` resolves `_EnvWrapper`, `_RpcStubWrapper`, `_BindingWrapper` and `_FetcherWrapper` to its own classes, and wrappers answer `_env`, `_ctx` and `_binding` with their JS object. A KV `arrayBuffer` read returns a `memoryview`, as in stock. The ASGI and WSGI adapters set `encodeBody: "manual"` when the app sets `Content-Encoding`, because both SDKs otherwise compressed a GZipMiddleware body a second time.

`patch_env` stays an exported name and raises `NotImplementedError`, because workerd removed the helper it needs on 2026-06-30. crosswind's docs list every fix on a "differences from the stock SDK" page.

### FFI escape hatch

Every wrapper exposes the underlying JS object as `js_object`, and every wrapper's constructor accepts a JS object. This extends the stock SDK's own convention from `Request` and `Response` to binding classes, `env` and `ctx`, so libraries that use it run on both SDKs.

```python
raw_namespace = self.env.COUNTER.js_object
response = Response(await stub.fetch(request.js_object))
```

Users import `to_js` and `create_proxy` from `pyodide.ffi` directly. crosswind does not re-export them.

### Entropy patches

Cloudflare snapshots memory after running a module's top-level code, and workerd blocks randomness during that run. numpy, pydantic_core, aiohttp, tiktoken and others use randomness on import. crosswind ports the stock SDK's per-package patches and loads them through a `.pth` hook, which Python runs at startup without an application import. workerd processes the hook when `python_process_pth_files` is on, which it is by default from 2026-05-26. Before that date workerd ships its own package patches. The second half of that comes from reading workerd source and has not been run. In production, numpy 2.2.5 deployed without the patches on dates before and after 2026-05-26, and each isolate drew different random values ([production checks](research/production-deploy-checks.md)). The port stays until the other patched packages are checked.

### pywrangler compatibility

crosswind requires Wynd for now. pywrangler always adds `workers-runtime-sdk` to its lockfile (`resolve.py:136`), so a pywrangler project that declares crosswind would install two packages into `python_modules/workers/`. crosswind checks `importlib.metadata` for `workers-runtime-sdk` at import time and raises a clear error. That check only runs if crosswind's files survived the overwrite. A pywrangler PR that skips injection when the project declares a `workers` provider is planned.

### Testing

Host unit tests cover wrapper logic with a fake `js` and `pyodide.ffi` layer, in the style of the agents port's `tests/_fake_ffi.py`. Integration tests run small Workers under the pinned `wrangler dev` for each target date (3.12, 3.13 and 3.14).

## Agents and containers ports

The ports in `../../agents-port/agents-py` and `../../containers-port/containers-py` must run on both SDKs. They declare no runtime SDK dependency, so containers-py drops `workers-runtime-sdk>=1.9.0`. They use only what both SDKs provide: `js_object`, constructors that accept JS objects, and camelCase calls on `ctx`. agents' `_raw_ctx` reads stock's private `_ctx` attribute today. It changes to check `js_object` first and `_ctx` second.

CI runs agents' `verify/` Worker twice, once with pywrangler and the stock SDK and once with Wynd and crosswind.

## Facts to verify during implementation

- Whether `site.bucket` works as an absolute path. Dry runs skip Workers Sites, so only a real deploy shows it.
- Which entropy patches are still needed. numpy 2.2.5 deployed and reseeded per isolate without them ([production checks](research/production-deploy-checks.md)). Checked 2026-10-13 under `wynd dev` on 2026-09-08 (3.14) with the hook deleted: pydantic, tiktoken, cryptography, jiter, rpds-py, uuid-utils, aiohttp, opentelemetry-api, fastapi and litestar fail to start, and numpy, requests, urllib3 and langsmith start. Every patch stays.
- Whether returning a rejecting thenable from a Workflow step callback makes the engine see a `NonRetryableError` ([research](research/workflows-without-js.md)). Verified 2026-10-12 in the local Workflows engine under `wynd dev` with wrangler 4.129.0, on 3.12 (2025-06-01), 3.13 and 3.14 (`crosswind-workers/tests/e2e/test_workflow_thenable.py`). With two retries allowed, the thenable named `NonRetryableError` ran once, and the same thenable named `OtherError` ran three times, so the name is what stops the retries. `run` sees the step's final error as `Error: NonRetryableError: stop`. On 2026-10-12 the same Worker, deployed with wrangler 4.129.0 to production on 2025-06-01 (3.12), 2025-10-01 (3.13) and 2026-09-08 (3.14), gave the same result on all three: `NonRetryableError` once, `OtherError` three times, each instance `complete`.
